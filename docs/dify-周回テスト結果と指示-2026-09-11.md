## A.【最優先・実害あり】着地後にトークへ直接書いた追記が、どこにも残りません

### 何が起きたか

⑭で、着地後にこう書きました。DV被害者の状況悪化の訴えです。

> あのあと夫から"出ていけ"と言われました。
> 夜も眠れていません。

**応答は2秒。定型文でした。**

```
[コード（期限切れの解除・経過ターン計算）] closing:"true" phase:"終了"
 → 追記本文抽出            … 動かず
 → 相談記録登録：追記       … 動かず
BOT: ご相談ありがとうございました。…▼ お伝えしたいこと・状況の変化（フォームのリンク）
```

**着地ロック（`IF/ELSE 7`）が手前で止めるため、追記の経路まで届いていません。**

### 作業記録の意図が、実際には成立していません

§2にこう書かれていました。

> **変えなかったこと（意図的）**
> 相談者がトークに直接書いた追記は、これまでどおり本文として扱います。
> 着地後に「あのあと上司から〜」と書き込まれた場合、この経路しかありません。
> ノードごと外すと、その言葉が台帳に残らなくなります。

**判断の方向は正しいです。** ノードを残したこと自体は適切でした。
ただ**ノードを残しても、ロックが先に効くため到達しません。**
「この経路しかない」と書かれたその経路が、着地後は塞がっています。

### 深刻さ

- 台帳に残りません
- Slackにも出ません
- **相談員は状況が悪化したことを知りません**
- 利用者にはフォームのリンクが返るだけです。そこから入力し直す方は多くないはずです

なお⑮の応答で、ボットはこの内容を覚えていました。

> 以前、「出ていけ」と言われたこと、夜も眠れていないと伺っていましたが、その後お変わりありませんか。

**会話の記憶には残るが、記録には残らない**状態です。
相談員だけが知らない、といういちばん困る形になっています。

### 対処案

`IF/ELSE 7` の着地ロックの**手前**に分岐を足し、
着地後の発話が相談内容らしい場合は**追記として記録してから**定型文を返す形を提案します。

```
コード（期限切れの解除・経過ターン計算）
  ↓
IF/ELSE（着地後の書き込みかどうか）        ← 新規
   条件： closing が "true"
        かつ interaction_pattern が "目的外" ではない
   ├ true → 追記本文抽出 → HTTP（相談記録登録：追記）→ 結果判定
   │          ↓
   └ false ──┴→ IF/ELSE 7（従来の着地ロック）
```

**判定には既存の `interaction_pattern` を流用できます。**
「目的外」を除けば、雑談や誤送信で行が増えることを防げます。

利用者への返信は定型文のままで構いません（**記録が残ることが目的**です）。
`max_support_need` が高いままの方については、**Slackへ速報を飛ばすこと**も
ご検討ください。危機の悪化を相談員が知る唯一の手がかりになります。

> 構造変更です。これまでどおり、**先にご自身で試してから公開**してください。


### 初回受付には判定ノードがありません

サマリーと追記には `コード（〜保存の結果判定）` が付きましたが、
**初回受付には付いていません。**

初回受付は最初の5往復で毎回走るため、多くの場合は次の回で入ります。
**ただし1〜2往復で離脱した方の記録は落ちます。**

いちばん支援が必要な方ほど、名乗っただけで離脱することがあります。

### 対処案

サマリー・追記と**同じ判定ノードを初回受付にも付けてください。**
失敗時は送り直し、それでも駄目ならSlackへ。すでに手本があります。
