9/11 の修正版に対して、本番のDifyアプリに実際に会話を流して検証しました。
その結果にもとづく指示です。上から順に着手してください。

検証方法：Dify の chat-messages API を `response_mode: streaming` で叩き、
`node_finished` イベントから各ノードの入出力まで確認しています。
画面には出ないHTTPノードの応答やパラメータ抽出の結果も見ています。

## 2. 【最優先】記録登録の404を解消する

### 症状

「HTTP リクエスト（相談記録登録：初回受付）」が **404 で失敗**しています。

```
status: exception
error_message: Request failed with status code 404
error_type: HTTPResponseCodeError
```

検証した会話では、このノードが走った**2回とも404**でした。
別の会話でも1回発生しています。

### 報告書の分析との違い

報告書では「GASへの書き込みが10秒の制限を超えている（`Unknown error`）」と
分析されていましたが、**私が観測しているのは 404 です。**

タイムアウトなら通常504か、GASからのエラー応答が返ります。
**404はURLそのものに届いていないことを示します。**

### 確認してほしいこと

**GASのウェブアプリのデプロイURLが変わっていないか**を確認してください。

- 「新しいデプロイ」を作ると **URLが変わります**。Dify側が古いURLのままだと404になります
- 既存デプロイの「デプロイを管理」→ 鉛筆アイコン →「バージョン」を上げれば **URLは維持されます**

バージョン16を公開されたタイミングと符合しないでしょうか。

### 手順

1. GAS の「デプロイを管理」で、現在有効なウェブアプリURLを控える
2. Dify の3つのHTTPノード（初回受付／引き継ぎサマリー／追記）のURLと突き合わせる
3. 食い違っていれば、Dify側のURLを差し替える
4. 今後は**必ず既存デプロイのバージョンを上げる運用**にする

### 確認のしかた

修正後、テスト会話を1往復流し、初回受付ノードの応答が
`{"ok":true,"row":NN}` になれば解消です。

> 引き継ぎサマリーは `ok:true` が返っているのに初回受付が404、という
> 状態であれば、ノードごとにURLが違っている可能性が高いです。
> 3つとも突き合わせてください。

## 3. 【次点】支援必要度8以上の即時Slack通知（残り3）

Slack通知は「IF/ELSE 10（着地したときだけ通知する）」でのみ発火します。
**利用者が途中で離脱したら、切迫したケースでも誰も気づけません。**

| 発話 | support_need | 即時通知 |
|---|---|---|
| 死にたい。今夜にでも実行しようと | 9 | なし |
| 薬を全部飲んで終わりにしようと | 10 | なし |
| 所持金200円・今夜泊まる場所がない | 8 | なし |
| 夫に毎日殴られている・今も家にいる | 8 | なし |

DVのシナリオでは8往復しても、着地するまで一度も通知が飛びませんでした。

### 手順

**先に会話変数を追加**：`crisis_alerted`（string、初期値は空）

1. 「コード（支援必要度の保持・フェーズ・着地判定）」の後ろに IF/ELSE を追加
   （名前：「危機の速報判定」）

2. 条件（AND）

| 変数 | 条件 | 値 |
|---|---|---|
| `max_support_need` | ≧ | `8` |
| `conversation.crisis_alerted` | 空 | — |

3. true 側に Slack通知のHTTPノードをつなぐ

```
{"text":"🚨 支援必要度が高い相談が進行中です\n必要度：{{#...max_support_need#}}\n種別：{{#...crisis_category#}}\n根拠：{{#...need_basis#}}"}
```

4. 通知の直後に変数代入ノードを置き、`crisis_alerted` に `true` を入れる
   （同じ会話で何度も飛ばないように）

> ⚠️ Bodyに **Enterで改行を入れないでください。** `\n` は2文字として入力します。
> 値に改行が入る `need_basis` を埋め込むので、**コードノードで
> `JSON.stringify` して組み立てるほうが安全です。**

> ⚠️ 構造変更なので、報告書の「自戒」のとおり、
> **先にご自身で試し、通ることを確認してから公開してください。**

## 4. LLM失敗の頻度を把握する

### 検証中に起きたこと

5往復目、相談者が「相談員さんに話を聞いてもらえるなら、お願いしたいです」と
伝えた**まさにその場面**で、LLMが失敗しました。

返ってきたのは、設定いただいたフォールバック文です。

> 申し訳ありません、ただいま混み合っております。少し時間をおいて、
> もう一度お話しかけていただけますか。お急ぎの場合は…いのちSOS：0120-061-338…

**フォールバックは正しく効いています。** 無反応にならず、緊急窓口まで
案内できました。6往復目には自ら詫びて話を戻しており、会話も壊れていません。
**この設定は非常に有効でした。**

### ただし、失敗そのものは起きています

残高切れではないタイミングでの失敗です。別の原因（タイムアウト、
レート制限、モデル側の一時障害）が疑われます。

**いちばん大事な場面で失敗したことは重く見てください。**
フォールバックがなければ無反応でした。

### 手順

1. Dify の「ログ＆アナウンス」でLLMノードの失敗率を確認する
2. 失敗時にSlackへ通知する分岐を足す
   （3と同じ形。LLMノードの例外分岐から通知ノードへ）
3. 頻度が高いようなら、モデルの変更（`gemini-2.5-flash` への切り替え等）や
   タイムアウト値の見直しを検討する
