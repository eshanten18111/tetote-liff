## 2. 欠陥④の直しかたは、実機で確かめて妥当でした

`looksStaleConversation` は「400は本文に会話のことが書かれているときだけ無効」に絞りました。
**絞りすぎて、本当に無効な会話を拾えなくなっていないか**が心配だったので、
実際に Dify に死んだ会話IDを投げて、何が返るかを測りました。

```
存在しないUUID      → status=404  {"code":"not_found","message":"Conversation Not Exists…"}
他人の会話ID        → status=404  {"code":"not_found","message":"Conversation Not Exists…"}
UUIDでない文字列    → status=400  {"code":"invalid_param","message":"…conversation_id must be a valid UUID…"}
（比較）満杯のとき  → status=400  {"code":"invalid_param","message":"…no space left on device"}
```

**本当に会話が無効なときは 404 で返ってきます。** 404 は無条件で無効とみなす側なので、
**絞ったことで拾えなくなる経路はありません。**
壊れた会話IDの400も、本文に `conversation_id` が入るので拾えます。
満杯の400には `conversation` が入らないので、正しく素通りします。

**この直しは、そのままで大丈夫です。**

### ひとつだけ、余地（急ぎではない）

判定は `/conversation/i` という広めの正規表現です。
**実機で当たることは上のとおり確かめました。** 一方で、

```
確かめていないこと：コードノードが落ちたときのエラー文に "conversation" が混ざるか
```

このワークフローは会話変数（conversation variables）を20個使っています。
もしエラー文に `conversation_variables` のような語が出ると、**満杯の400と同じ種類の
一時的な失敗なのに「会話が無効」と判定してしまいます**（＝直したはずの事故が再発する）。

実測した2つの文だけを見るなら、こう狭められます。

```js
return /Conversation Not Exists|conversation_id/i.test(String(data.body || ''));
```

**上の4ケースすべてで判定は変わりません**（確認済み）。
デプロイ前なら足すのは無料なので、ついでにどうぞ。**必須ではありません。**

## 3. 見つかった穴：`p.at` は「受け取り時刻」ではなくなる

**ここだけ、デプロイ前に直してください。**

門はこう書かれています。

```js
const ready = await fetchReadyAnswer(env, userId, p.text || '', Number(p.at || 0));
...
if (sinceMs && created > 0 && created * 1000 < Number(sinceMs) - 60000) return null;
```

`p.at` を「受け取り時刻」として渡しています。**ところが `p.at` は、途中で書き換わります。**

```js
p.tries = Number(p.tries || 0) + 1;
p.at = Date.now();          // ← 聞き直す直前に、いまの時刻で上書きされる
```

`p.at` は**2つの役目を兼ねています。**「いつ受け取ったか」と「次にいつ触ってよいか（鍵の時計）」です。
鍵の時計として更新された瞬間に、**受け取り時刻としては嘘になります。**

### 実際に起きること（再現しました）

```
シナリオ：1通目が遅く、最初の聞き直しが失敗した回
 t=0     相談者が「はい」を送る（Difyには行が出来て、返事も書けている）
 t=180s  3回覗いても間に合わず、聞き直した → それも失敗（tries=1, p.at=180s に更新）
 t=300s  次の拾い直し。できている返事は配られるか？

 配られたもの      : 聞き直して作り直した返事
 AIに聞き直した回数: 1
 判定: NG できている返事を捨てて作り直した
```

対照（聞き直しが一度も無い回。`p.at` が受け取り時刻のままの回）：

```
 配られたもの      : 本当の返事（t=0に書けている）
 AIに聞き直した回数: 0
```

**門が、今回の返事を「昨日の行」と間違えて捨てています。**
そして捨てたあと `askDify` に落ちるので、

```
・同じ質問にAIが2回答える（料金も2回）
・相談者が見ていない返事が、Difyの履歴にもう1通残る
```

**これは、このパッチが止めようとしている事故そのものです。**
起きるのは「1通目が遅く、かつ最初の聞き直しも失敗した回」――
つまり**いちばん助けが要る回**です。

### 原因はこちらにあります

私が出した案が `sinceMs` に何を渡すかを書かず、`p.at` を渡す前提で書いていました。
`p.at` が鍵の時計を兼ねていることに気づいていませんでした。**すみません。**

### 直しかた（2行。`recv_fix_20260914.diff` を添えました）

受け取り時刻を**別の名前で、一度だけ**持たせます。

```diff
-        JSON.stringify({ text, at: Date.now(), tries: 0 }),
+        JSON.stringify({ text, at: Date.now(), recv: Date.now(), tries: 0 }),
```
```diff
-      const ready = await fetchReadyAnswer(env, userId, p.text || '', Number(p.at || 0));
+      const ready = await fetchReadyAnswer(env, userId, p.text || '', Number(p.recv || p.at || 0));
```

`recv` は**どこでも書き換えません。** `p.recv || p.at` にしてあるので、
**デプロイの瞬間にKVへ残っている古い pending（`recv` を持たない）も、これまでどおり動きます。**

当てて流し直した結果：

```
作業側の47件        → 合格 47 / 不合格 0（変化なし）
上の再現シナリオ    → 配られたもの: 本当の返事 ／ 聞き直した回数: 0 ／ 判定: OK
```

`worker_gate_test.mjs` として再現を残しました。`node worker_gate_test.mjs <全文のパス>` で動きます。

## 5. 2段返しの判断について（`実装判断-2段返し` へ）

**§5「1段目を新しく作らない」に同意します。** 理由3つは、こちらの測定とも矛盾しません。
とくに「6通目以降は24秒超が0%」なので、前に1通足すと**速い回に必ず無駄な1通が挟まります。**

**§5の後半（お待たせ通知を24秒→最初の覗きまで遅らせる案）についてだけ、
測っていない前提が1つあります。**

> 「…」表示は60秒もつ

**私はこれを測っていません。** LINEのローディング表示の持続時間は公式に
「最大60秒、または次のメッセージを送るまで」とされていますが、
**この相談システムで実際に何秒で消えるかは確かめていません。**

もし実際には短い（あるいは機種で違う）場合、45〜60秒まで文字が何も出ない時間が
**完全な無反応**として相談者に見えます。**「死にたい」と書いた直後だと重いです。**

> **提案：決める前に、テスト用のLINEアカウントで一度だけ実測してください。**
> 「…」を出してから何も送らずに、何秒で消えるかを見るだけです。
> **本番の相談者では試さないでください。** 私はLINEの画面に手が届かないので測れません。

§6（打ち手A）§7（GAS側の実行時間を先に測る）§8（プッシュ通数）については、
**こちらから足すことはありません。** 順番の提案（§9）にも同意します。
