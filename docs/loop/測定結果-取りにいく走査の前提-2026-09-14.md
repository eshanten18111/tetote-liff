測定日：2026-09-14（Dify の障害が復旧したあと）
対象：作業側パッチの `fetchReadyAnswer` / `findConversationId`
目的：実装したときに弊害・障害にならないかを、前提ごとに実機で確かめる

前回「Dify の sandbox が満杯（`no space left on device`）で 400」と報告した件は、
**復旧を確認しました。** `POST /v1/chat-messages` が正常に返り、返事も生成されます。

## 結論（先に）

**4つの前提すべてが、実機で正しいことを確認しました。この2つの関数は、このまま出して大丈夫です。**

前回「危ないかもしれない」と書いた2点は、**私の心配のしかたが間違っていました。**
実機ではどちらも作業側の書いたとおりに動きます。以下、測った中身です。

| # | 確かめたこと | 結果 | 実装への影響 |
|---|---|---|---|
| ① | `GET /messages` の並び順 | **古い順（末尾が最新）** | 後ろから走査するのは**正しい** |
| ② | `limit=3` は古い3件か新しい3件か | **新しい3件**（それを古い順で返す） | 会話が長くなっても**最新を見落とさない** |

## ① `GET /messages` の並び順 ― 古い順（末尾が最新）

「はい」を2回はさんだ会話を実際に作って、一覧を取りました。

```
[0] created_at=1789400937 q='呼び名：順序テスト／年代：40代／都道府県：東京'
[1] created_at=1789400957 q='はい'        ← 古いほうの「はい」
[2] created_at=1789400976 q='つらいです'
[3] created_at=1789401000 q='はい'        ← 新しいほうの「はい」
ORDER: OLDEST_FIRST（末尾が最新）
```

作業側の走査（`for (let i = list.length - 1; i >= 0; i--)`）をそのまま再現すると：

```
-> 拾ったのは index=3 created_at=1789401000
   answer='ありがとうございます。ゆっくりで大丈夫ですからね。順序テストさんのペースで…'
```

**新しいほうの「はい」の返事を拾いました。** コメントの「新しいものから見る」は前提どおりです。

---

## ② `limit=3` は「新しい3件」

ここが、私が前回いちばん見落としていたところです。
もし `limit` が**古いほうから**3件を返す仕様だったら、会話が4往復を超えた時点で
**最新の返事が窓に入らなくなり、取りにいく仕組みが丸ごと効かなくなります。**
4往復の会話で `limit` を変えて確かめました。

```
limit=1 → [0] created_at=1789401000 q='はい'          （最新1件だけ）
limit=2 → [0] 1789400976 'つらいです' / [1] 1789401000 'はい'
limit=3 → [0] 1789400957 'はい' / [1] 1789400976 'つらいです' / [2] 1789401000 'はい'
```

**新しいほうから N 件を切り出し、それを古い順に並べて返します。**
`limit=3` のままで問題ありません。会話が何往復になっても窓は最新に張り付きます。

## ③ `GET /conversations` の既定の並び ― `-updated_at`

`sort_by` を書いていないので既定に依存している、と前回指摘しました。
**既定が何かを実際に測りました。**

「作られたのは古いが、さっき動かした会話」を1つ用意して、順番が入れ替わるかを見ます。
（`created_at` 順なら動かない／`updated_at` 順なら先頭に来る）

```
掘り起こす前： [0] 4e0a6763 (created=…937)  [1] ff377818 (…902)  [2] 42839bcf (…863)
42839bcf に1通送る
掘り起こした後：[0] 42839bcf created=1789400863 updated=1789401069  ← 先頭に来た
               [1] 4e0a6763 created=1789400937 updated=1789400999
               [2] ff377818 created=1789400902 updated=1789400902
```

**既定は `-updated_at`（最後に動いた順）です。** `created_at` 順ではありません。

これは `findConversationId` にとって**望ましいほう**です。
この関数が欲しいのは「いま動いている会話」であって「いちばん新しく作られた会話」ではないからです。
日をまたいで戻ってきた相談者が、前の会話の続きを送った場合でも、正しくその会話を拾います。

### `sort_by` を明示するかどうか

**この設定が存在することは確かめました。** 値は4つだけで、それ以外はエラーになります。

```
sort_by=bogus_field → {"code":"invalid_param","message":"Input should be
 'created_at', '-created_at', 'updated_at' or '-updated_at'"}
```

そして `sort_by=-updated_at` を明示した結果は、**書かなかったときと完全に同じ**でした。

> **判断：いま直す必要はありません。** 挙動は変わらないので、これは不具合の修正ではなく、
> 「将来 Dify 側が既定を変えたときの保険」です。
> 次にこのファイルを触るついでに `&sort_by=-updated_at` を足す、で十分です。
> **このためだけに再デプロイする価値はありません。**

## ④ いちばん大事だったところ ― 生成中の行は一覧に出るか

ここが、前の返事を配ってしまうかどうかの分かれ目です。

- 生成中の行が**一覧に出ない**なら → 走査は1つ前の「はい」に当たり、**前の返事を配ってしまう**
- 生成中の行が**空の答えとして出る**なら → `if (!answer) return null` が効いて、**配らずに待つ**

生成中に一覧を2秒ごとに叩いて、作業側の走査が何を返すかを記録しました。

```
t+ 0.7s 窓=[はい(…957), つらいです(…976), はい(…1000)]
        => 取得: 'ありがとうございます。ゆっくりで大丈夫ですからね…'   ← 前の返事（危ない瞬間）
t+ 2.9s 窓=[つらいです(…976), はい(…1000), はい(…1138)]
        => 取得: null（=まだ→再試行）                                ← 新しい行が現れた
t+ 5.1s 〜 t+20.5s  ずっと null（= 待つ）
t+22.8s => 取得: '何度も「はい」と返信をくださり、ありがとうございます…'  ← 今回の返事
```

**新しい行は約3秒で一覧に現れ、それ以降は空の答えとして見えます。**
`!answer` の門がそこから最後まで効き続け、**前の「はい」の返事は一度も配られませんでした。**

### 残る「危ない瞬間」は、実際には踏めません

上の `t+0.7s` の1行だけが危ない窓です。**幅は3秒未満**。
ただし worker が覗きにいくのは、いちばん早くても受け取りから **30秒後**です。

```js
const waitMs = Number(p.tries || 0) === 0 ? FIRST_PICKUP_MS : LOCK_MS;  // 30000 / 120000
if (Date.now() - Number(p.at || 0) < waitMs) { stat.skipped++; continue; }
```

**3秒の窓に対して、いちばん早い覗きが30秒後。10倍の余裕があります。**
この窓は踏めません。**追加の対策は要りません。**

## 妥協点として残るもの（急ぎではない）

ここから先は「起きたら困るが、起こすのが難しい」話です。
**いま直さなくてよいと考えています。** 記録として残します。

### 会話IDが無く、かつ Dify に行が1つも出来なかったとき

`fetchReadyAnswer` は、拾った行が**今回のものかどうか**は見ていません。
同じ文面（「はい」など）なら、昨日の行でも一致します。

これが問題になるには、**次の3つが同時に**必要です。

1. KV に会話IDが無い
2. 今回の送信が Dify に**1行も作らなかった**
3. その方の前の会話の最後の3件に、**今回と同じ文面**がある

**2 が、思っていたよりずっと起きにくいことが分かりました。**
今回の測定中、こちらには `upstream request failed`（本文が返ってこない）が2回起きました。
そのときの Dify 側を後から見ると：

```
ff377818 [0] q='呼び名：順序テスト…'  answer_len=68  '順序テストさん、ご連絡いただきありがとうございます…'
42839bcf [0] q='呼び名：順序テスト…'  answer_len=64  '順序テストさん、ご連絡いただきありがとうございます…'
```

**返事は最後まで生成され、保存されていました。** つまり
「こちらにエラーが返った＝Dify では何も起きていない」ではありません。
**行が1つも出来ないのは、接続そのものが成立しなかったときだけ**です。

> **判断：いま入れなくてよい。** 3条件が重なる確率が低く、④で見たとおり
> 通常の経路では新しい行が3秒で出来るので、そもそも古い行に当たりません。
>
> 将来もし入れるなら、1行で足ります（`created_at` が一覧に含まれることは確認済み）：
> ```js
> // 今回の受け取りより前の行は採らない（60秒の余裕を見る）
> if (Number(m.created_at || 0) * 1000 < Number(sinceMs || 0) - 60000) return null;
> ```
> `sinceMs` には pending の `p.at` を渡します。
> **ただしこれは机上の案です。実機では試していません。**

### ついでに分かったこと：エラーが返っても料金は発生している

上のとおり、`upstream request failed` の2回とも**生成は完走していました。**
「エラーだったから、もう一度送る」を素直にやると、**同じ相談に2回課金され、
相談者が見ていない返事が履歴に1通残ります。**

worker はこれを既に知っていて、聞き直しを最後の手段にしてあります
（`PEEK_MAX` 回覗いてから `askDify`）。**この設計は正しいです。**
Gemini の予算アラートを立てておく理由が、ひとつ増えました。

## 測定に使ったもの

- `POST /v1/chat-messages`（blocking）で「はい」を2回はさんだ会話を作成

- `GET /v1/conversations?user=…&limit=5[&sort_by=…]`
- 生成中に2秒間隔で一覧を叩き、作業側の走査ロジックを Python で再現して突き合わせ
- 使ったのはテスト用の利用者IDだけです。**本番の LINE には触れていません。**
