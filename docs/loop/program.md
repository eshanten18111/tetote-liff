読む相手：**自律ループのエージェント**（人ではありません）
対象：一般社団法人 地域福祉サポートセンター てとて／LINEチャット相談システム
作成：2026年9月14日

## 0. これは何をするループか

`karpathy/autoresearch` と同じ形で回します。

```
① いまの設定を測る → ② 仮説を1つ立てる → ③ 設定を1つだけ変える
   → ④ 人が公開する（ここだけ人の関門）→ ⑤ 測り直す
   → ⑥ 良くなったら残す／悪くなったら戻す → ①へ
```

**train.py にあたるのが Dify ワークフローの設定**、**val_bpb にあたるのが返事の所要時間**です。

### この題材が autoresearch と違う点（先に読むこと）

| | autoresearch | ここ |
|---|---|---|
| 実験の反映 | エージェントがコードを書けば即反映 | **「公開」が要る。公開は人だけ**（`[Production Deploy]` で機械的に塞がれている） |
| 実験1回の時間 | 5分固定 | **約4分**（8サンプル） |
| 失敗の代償 | 数値が悪くなるだけ | **相談者に届く返事が変わる。命に関わる場面がある** |

**したがって、③と④のあいだで必ず止まること。** 勝手に公開しようとしても塞がれます。塞がれたら迂回せず、人に渡して待つこと。

## 1. 目的（この数値を下げる）

**主指標**

```
over24pct … 返事が24秒を超えた割合（%）。1通目だけでなく、全局面で測る
```

> **定義を変えた（2026年9月14日 18:42）。** もとは「**1通目**の返事が24秒を超えた割合」だった。
> **2通目以降も同じくらい超えている**ことが分かったため、全局面に広げた。
> ループの指摘は正しい。1通目に限っていると、2通目以降の改善・悪化が数字に出ない。
>
> **3局面に分けて記録すること**（仕組みが違うので、混ぜると原因が見えなくなる）。
>
> ```
> 1通目        … カルテ照会あり・初回受付あり（GAS 2本）
> 2〜5通目     … 初回受付あり（GAS 1本）
> 6通目以降    … GASを1本も通らない。LLMだけ
> ```

24秒は、Worker が Dify を待つのをやめる時刻です（`ANSWER_TIMEOUT_MS`）。
ここを超えると、相談者にはいったん「お待たせしています」だけが届き、本文は1分ごとの拾い直しで後から届きます。

> **2026年9月14日 21時台の訂正。** ここには「24秒は Cloudflare が返答を待てる窓」「超えると
> Worker が問い直して同じ相談が二重に処理される」と書いてあったが、**どちらも正確ではなかった。**
> 本当の壁は waitUntil の**約30秒**で、24秒はその内側で決めた見切り時刻。
> 二重処理も「24秒を超えたから」ではなく、**1通目が遅いと会話IDが保存されないまま
> 打ち切られるため**に起きていた（§9①で修正済み・デプロイ待ち）。

**目標：over24pct ≤ 20**

**副指標**

```
p50 … 中央値（秒）。目標 ≤ 20
max … 最大値（秒）。120秒超（ゲートウェイの504）を1回も出さない
```

**守るべき制約（これを壊した実験は、数値が良くても破棄）**

```
・追記の定型文（「追記いただいた内容を承りました」）が1通目・2通目に出ない
・返事が「聴く」内容になっている（人が読んで判断する）
```

## 2. 測り方（実験1回の手順）

1. Chrome で Apps Script のプロジェクトを開く
   （URLは人に聞くこと。**この文書には書かない**。
   　この文書は公開リポジトリに置かれることがあるため）
2. 左のファイル一覧から **`sim_chat.gs`** を選ぶ
3. 関数ピッカーが **`simRun`** になっていることを確認する（`simRun` はファイルの先頭にあるので既定で選ばれる）
4. 「実行」を押す
5. 実行ログから **`RESULT=` で始まる1行**を拾う

```
RESULT= n=8 p50=35.6 min=18.9 max=61 over24=4 over24pct=50
```

**約4分かかります。** Apps Script の6分上限に当たらないよう、4分半で自動的に打ち切ります（`時間切れのため◯回で止めます` と出る）。

### ピッカーが言うことを聞かないとき

関数一覧は仮想化されていてクリックが届かないことがあります。**一覧を操作しないこと。** 代わりに、

- `sim_chat.gs` の**先頭の関数**が `simRun` であることを確かめる（ピッカーはファイルの最初の関数を既定で選ぶ）
- 別のものを測りたいときは、**一覧を触らず `simRun` の中身を書き換える**

この形にしてあるのは、**取り違えて `doPost` を走らせる事故を防ぐため**でもあります。

### n=8 では足りないとき

`sim_chat.gs` の `simLoop` の `N` を増やす。ただし1回の実行は6分で切られるので、**N は 8 以上にしないこと**。数を増やしたいときは**実行を複数回**に分ける。

### ノードごとの所要時間を取る（`simRun` より速く、内訳が出る）

**公開API** `/v1/chat-messages` をストリーミングで叩くと、`node_finished` イベントに各ノードの
`elapsed_time` が入る。**管理用API（`/console/api`）の認証は要らない。** アプリのAPIキーだけでよい。

```bash
export DIFY_API_KEY='app-xxxxxxxx'
python3 nodetime.py       # 既定で6回。N を書き換えれば増やせる
```

出るもの：

```
=== 実行3  実測 20.2秒 ／ ノード合計 17.4秒 ／ 差 2.8秒
      8.11秒  LLM
      2.79秒  HTTP リクエスト（カルテ照会）
      2.35秒  パラメータ抽出
```

**「実測」と「ノード合計」の差**が §7 の仮説C（固定費）を、**同じノードの max と min の開き**が
仮説B（時々詰まる）を、それぞれ直接測る。

Apps Script の6分上限も、n=8 の縛りも、4分半の打ち切りもない。
`simRun` は「相談者から見た所要時間」を測るのに残し、**原因の切り分けにはこちらを使う。**

スクリプト：`tools/dify-test/nodetime.py`
（`eshanten18111/tetote-liff` の `claude/dify-testing-continued-j1xrb4`）

> この節は2026年9月14日に追加した。それまで program.md には
> 「Difyのログ画面には内訳が出ず、APIは401で閉じている」と書いてあったが、**誤りだった。**
> 401なのは管理用APIだけで、公開APIのストリーミングでは内訳が取れる。
> この誤りのせいで、ループは測れるものを測らず時間帯の調査へ回された。

### F. 次に測ること — 300秒は「返らない」のか「301秒で返る」のか

`nodetime.py` は **300.0秒で打ち切っている**。つまり、

- LLMが永久に返らないのか
- **301秒で返ってくるのに、こちらが300秒で諦めているのか**

が**まだ区別できていない。** 300という数字は、モデルの思考時間ではなく
**読み取りタイムアウトの既定値**の匂いがする。

Dify のプラグインには、**共有セッションの古いコネクションが 300秒の読み取りタイムアウトに当たり、
1秒後の再試行で成功するのに合計301秒を「成功」として報告する**という既知の形がある
（`langgenius/dify-official-plugins` #3815。報告例は Tongyi の埋め込み経路）。
**同じ形であれば、原因はモデルの遅さではなく接続プールで、設定では直せない。**

**やること：`nodetime.py` のタイムアウトを 360秒に上げて、跳ねを1回捕まえる。**

| 結果 | 意味 | 次 |
|---|---|---|
| 約301秒で完了する | 接続プールの読み取りタイムアウト。プラグイン側の問題 | Dify/プラグインの更新を待つ。並行して §9② |
| 360秒でも返らない | 別の仕組み | ノード内訳を添えて Dify に報告 |

どちらでも**ループ側の打ち手は増えない。** この測定は「§9② に渡す根拠」を固めるためにやる。

### G-3. 「最悪32秒」は取り消す（2026年9月14日 18:06 の測定を受けて）

18:06 の12回で、**カルテ照会 58.29秒・初回受付 72.76秒**が出た。
§7G に書いた「1回15秒・再試行1回で最悪32秒」では説明がつかない。**あの式は取り消す。**

取り消す理由（httpx の読み取りタイムアウトの意味）：

```
connect / read / write のタイムアウトは「全体の上限」ではない。
read は「バイトが1つも来ないまま経過してよい時間」の上限である（間隔の上限）。
したがって、少しずつでもデータが返ってきている相手には発火しない。
→ 応答が「止まらずに遅い」場合、合計時間に上限は無い。
```

**これは仕組みの話であって、この系で起きていることの確認ではない。**
候補は3つあり、**まだ区別できていない**（§7G-4 で測る）。

```
候補① 応答が「止まらずに遅い」→ read タイムアウトが発火せず、上限なく延びる
候補② リダイレクトを追っている（GASのPOSTは302を返す）→ 1ホップごとにタイムアウトが付き直す
候補③ 再試行が設定より多く走っている
```

**打ち手Bの効き（17.25秒 → 最悪8秒）も、同じ理由で取り消す。**
候補①なら、`read` を5秒に詰めても合計は縮まない。**Bは弱い手になる。**
そのとき強いのは **打ち手A（そもそも待たない）** である。

### G-4. 並列に走っているのはどこか（2026年9月14日 確認。推測ではない）

18:06 の実行7で `実測 102.5秒 ＜ ノード合計 108.3秒` が観測された。
下書きの辺を全部数えて、**同じ出力から複数の辺が出ている箇所は3つ**だと確認した。

```
① LLM → 返信整形（サマリー除去） ／ パラメータ抽出3（有人対応同意）
② 追記本文抽出 → HTTP（相談記録登録：追記） ／ コード（着地後書き込みの速報判定と本文）
③ HTTP（相談記録登録：初回受付） → 変数代入（初回受付ログ済みフラグ） ／ コード（初回受付の保存の結果判定）
```

**①が1通目で効く**（パラメータ抽出3 は2〜3秒。返事の整形と同時に走る）。②は2通目以降。

そして重要なのは次の事実である。

```
HTTP（カルテ照会）      入ってくる辺は1本（IF/ELSE 16 のみ）  → 直列
HTTP（初回受付）        入ってくる辺は1本（IF/ELSE 8 のみ）    → 直列
```

**この2つのノード自身は並列に走っていない。** 並列なのは「初回受付の**後ろ**の2本」である。

**したがって、`実測 − そのノードの時間` という引き算は、この2つについては成り立つ。**
「ノード合計 > 実測 なら式を使うな」という止め方は**書いた側（人間）の誤りだった。**
止める条件は「**そのノードに入る辺が2本以上ある／並列区間の中にある**」でなければならなかった。
