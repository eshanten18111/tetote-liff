## 2. 今回あらたにやったこと ― 本物の Dify API に当てた

**ここまでのテストは、Dify を偽物に差し替えて手順だけを見るものでした。**
58件すべてがそうです。つまり、

```
確かめられていたこと：手順（覗く→送る／空振り→数える→最後に聞き直す）
確かめられていなかったこと：**本物のDifyに対して、URLの組み立てと戻り値の解釈が合っているか**
```

パッチで `/conversations` の呼び出しが新しく増え、`/messages` の読み方も変わりました。
**そこが本物に当たるかは、誰も試していませんでした。** 試しました。

やりかた：**KVだけ偽物。HTTPは本物**（`api.dify.ai`）。
パッチ後の `fetchReadyAnswer` / `findConversationId` を**そのまま**動かしています。

実機で新しく会話を1つ作り（利用者IDはテスト用）、そこへ当てた結果：

```
対象の会話: 4cb0689d-…  ／ 探す文面: "はい"
  窓(limit=3): 呼び名：実機テスト／@1789405999 / はい@1789406015

【1】KVに会話IDがある
  OK  できている返事を返した
     先頭: お返事ありがとうございます。/何から話せばいいか、迷われることもありますよね。/

【2】KVが空 → 本物の /conversations から会話IDを拾えるか
  OK  会話IDを復元してKVに入れた
  OK  返事も取れた
     叩いたURL: /conversations?user=…&limit=1&sort_by=-updated_at
                /messages?conversation_id=4cb0689d-…&user=…&limit=3

【3】門：受け取り時刻がその行よりずっと後なら、配らない
  OK  古い行として弾いた（null）

【4】門：60秒の余裕の内側なら、配る
  OK  55秒ずれていても配った

【5】findConversationId 単体
  OK  いま動いている会話を返した（対象と一致）
```

**欠陥①の直し（会話IDが無いとき Dify に尋ねて拾う）が、本物に対して通ることを確認しました。**
URLも意図どおり組み立てられています（`sort_by=-updated_at` が付いている）。

### この実機テストの断り

```
・認証ヘッダだけ外して投げています（この環境ではプロキシが鍵を入れるため）。
  URLの組み立てと戻り値の解釈を見るのが目的で、**認証は試していません**
・node の fetch はこの環境のプロキシを通らないので、curl 経由に差し替えています。
  差し替えたのは「外に出る部分」だけで、Worker のコードはそのまま動かしています
・LINEへのプッシュは呼んでいません（retryPending ではなく、2つの関数を直接叩いています）
```

`tools/dify-test/worker_live_test.mjs` として残しました。

### 途中で1回 NG が出ましたが、コードは正しかったです

最初、別の利用者IDで試したとき【2】が NG になりました。**私のテストの誤りでした。**
その利用者には、以前の測定で作った会話が他にもあり、`findConversationId` は
**そのうち最後に動いたもの**を返していました。**それが正しい動きです。**
（`-updated_at` は「いま動いている会話」を返すためのものなので、期待したこちらが間違い）
利用者を新しくして測り直したのが上の結果です。
