## 1. いちばん重要な制約：1段目は Dify を待てません

```
first_token と実測の差   p50 1.4秒
1通目の first_token      p90 76.1秒
```

**Dify から最初の文字が届くのは、返事が完成する1.4秒前です。**

つまり「Difyの出力が流れ始めたら1段目を送る」という設計は成立しません。
**1段目は、Worker が Dify を呼ぶのと同時に、待たずに送る**しかありません。

### ここが実装の分かれ目です

```
Worker が LINE の webhook を受ける
   ├─ すぐ 1段目を送る（Dify を待たない）        ← 0秒
   └─ Dify を呼ぶ → 返ってきたら 2段目を送る     ← 18〜80秒
```

**1段目は「Difyが何を返すか知らない状態」で書かれます。** 名前も呼べません。
カルテ照会が終わっていないためです。

## 2. 決めていただきたいこと（4つ）

### ① 1段目に何を書くか

**相談者は必ず2通受け取ります。** 1通目は中身のない文になります。

懸念されるのは、**「死にたい」と書いた直後に定型文が返る**場面です。

| 案 | 文例 | 懸念 |
|---|---|---|
| ア：受け止めだけ | 「お話しくださって、ありがとうございます。いま読んでいます。少しお待ちください。」 | 切迫した方には冷たく映る可能性 |
| イ：受け止め＋窓口 | 上に加えて「お急ぎの場合は いのちSOS 0120-061-338」 | **毎回窓口が出る。**「窓口を案内するときの絶対のルール」（プロンプト §4 の削ってはいけない章）と衝突しないか要確認 |
| ウ：出さない場面を作る | 2通目以降だけ2段返しにする | **1通目が over24pct 67% で最悪。**そこを外すと効果が薄い |

**私の見立て**：アを基本にし、**イは「Dify が返せなかったとき」だけに限る**のが、
いまのプロンプト設計と衝突しません。窓口の出し方は既存の規則が厳密に決めているので、
**Worker が独自に窓口を出す設計は、その規則の外側に新しい経路を作ることになります。**

### ② 1段目を出す条件

**常に出すか、遅いときだけ出すか。**

| 案 | 動き | 引き換え |
|---|---|---|
| 常に出す | 必ず2通 | 速い回（6通目以降 p50 22.2秒）でも2通になる |
| **N秒待って、返らなければ出す** | 速い回は1通のまま | Worker 側にタイマーが要る。**24秒の窓の内側で切る必要がある** |

**後者を推します。** 6通目以降は over24pct 0% なので、**そこで2通になるのは損です。**

閾値の目安（今回の実測から）：

```
6通目以降   p50 20.1 / p90 21.5 / max 21.8（first_token）
2〜5通目    p50 17.5 / p90 34.3
1通目       p50 56.9 / p90 76.1
```

**15秒で切ると、6通目以降のほとんどが2通になります。**
**20秒で切ると、6通目以降は1通のまま、1通目はほぼ2通になります。**

ただし**Cloudflare Worker の24秒の窓の内側で送り切る**必要があるので、
**タイマーは20秒より手前**でなければ間に合いません。ここは Worker の実装を読んで詰める必要があります。

### ③ いまの「二重処理」をどうするか

`program.md §1` にこうあります。

> 24秒を超えると、相談者には「お待たせしています」という代替の文だけが届き、
> **Worker が問い直して同じ相談が二重に処理されます**

**2段返しを入れると、この問い直しは不要になります。**

ただし確認が要ります。**いま二重処理が「結果的に救済」になっている経路はありませんか。**
たとえば1回目が落ちても2回目で記録が入る、という形になっているなら、
**それを外すと記録が落ちます。**

Worker の該当箇所（387行付近）を読まないと分かりません。**作業側への確認事項です。**

### ④ 打ち手Aをやるか

| 局面 | 実測 over24pct | → 打ち手A |
|---|---|---|
| 1通目 | 67% | **67%（変わらず）** |
| 2〜5通目 | 33% | **17%** |
| 6通目以降 | 0% | 0% |

**2〜5通目には効きます。1通目には効きません。**

**副作用**：初回受付を回答より後ろに動かすと、
**保存の失敗検知（`IF/ELSE 14`）も後ろに移ります。**
失敗しても相談者にはすでに返事が届いているので、**救済がSlack通知だけになります。**

いまは同期なので、失敗時に何かできる余地がありました。
**2段返しを入れるなら、どのみち非同期になるので、この差は小さくなります。**

**2段返しと同時にやるほうが、手戻りが少ないと思います。**

## 3. 実装しても解決しないこと（期待値の調整）

**2段返しは「相談者を待たせない」ための手であって、「返事が速くなる」わけではありません。**

```
1通目の本文が届くまで   p50 58.4秒 ／ p90 77.6秒
```

**1段目を送っても、本文は1分後に届きます。**
相談者は「読んでいます」という文を受け取ったあと、**1分待ちます。**

これが許容できるかは運用の判断です。許容できないなら、**別の手が要ります。**

| 手 | 状態 |
|---|---|
| `thinking_budget` を下げる | Dify 側に残る唯一の候補。**見立ての深さと引き換え。§5の安全確認が要る** |
| カルテ照会を1通目から外す | 「2回目の相談で覚えている」が失われる。**昨日入れた機能を戻すことになる** |
| GAS を速くする | 受け口はすでに1.2〜1.4秒。**遅いのは Google の転送層で、こちらから短縮できない** |

**カルテ照会を外す案は、いま挙げておきます。** 1通目の遅さの主因はここです
（62.69秒を観測）。ただし**昨日実装した機能を打ち消す**ので、
速さと「覚えていること」のどちらを取るかの判断になります。

## 5. 数字の限界（承知しておいていただきたいこと）

- **1通目は n=3 です。** over24pct 67% は3回中2回という意味で、幅があります
- **時刻によって大きく変わります。** 17:38 は over24pct 33%、18:06 は 58%、今回（18:58）は 29%（全体）
- **GASの遅さには上限が見えていません。** 105.6秒を観測しており、
  「最悪でも何秒」と言える根拠がまだありません

**閾値を決めるときは、p90 ではなく max を見ておくほうが安全です。**
