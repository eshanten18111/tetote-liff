## 0. まず、いただいた指摘への回答

### 「`status_code ≠ 200` だけでは足りない」— そのとおりです

`doGet` の応答が `status 200` かつ `{"ok":true,...}` で返る以上、
**私の指示のままなら見逃していました。** 判定を「200であること」＋
「預かった印（`queued` か `row`）があること」の両方にした対処が正しいです。

実測でこの形の失敗を捕まえられたことも大きいです。

**相談者自身が書く文章が入る箇所のほうが危険**だという点を見落としていました。

初回受付と追記は相談者への返信より前に走るため、リトライを増やすほど
待たせることになります。**私の指示（3ノードとも）より、そちらの判断が適切です。**

## 3. 【最優先】追記の本文が記録されていません

### 実データ

```
[追記本文抽出] addendum_text : "受付しました"
               addendumText  : "受付しました"
               rescue        : "追記の本文：\n受付しました"
```

**相談者の言葉ではなく、固定文字列「受付しました」が台帳に入っています。**
退避Slack通知も「追記の本文：受付しました」となり、手で写す手がかりになりません。

### これは `addendum.py` の不具合ではありません

コードは正しく動いています。**問題は入力側です。**
`form2.html` がトークに送るのは合図の1行だけだからです。

```js
// form2.html
var MARKER = {
  note:  '追記フォーム回答：受付しました',
  close: '追記フォーム回答：受付しました'
};
// 本文は Worker へ直接送られ、トークには出ない（659行目付近のコメントに明記）
```

`addendum.py` のコメントには「追記の本文は相談者ご自身の言葉です」とありますが、
**この前提が成り立っていません。**

### 確認していただきたいこと

1. **Worker が Dify へ渡すメッセージに、追記本文を差し込んでいますか。**
   - 差し込んでいる → 問題なし。私の指摘は杞憂です
   - 差し込んでいない → `stage:addendum` の行は「いつ追記があったか」しか記録できていません
2. **支援経過シートの既存の追記行を見て、本文が「受付しました」になっていませんか。**

### これは今回の修正で生じたものではありません

以前からこうだった可能性が高いです。今回 `rescue`（退避本文）を作るようになって、
**初めて中身が目に見えるようになった**だけだと思われます。

### 直すとすれば

追記本文は Worker が持っています。**Worker から GAS へ直接送る**のが素直です
（Dify を経由させる必要がありません）。
Dify 側の `addendum` 経路は「追記があった」という事実の記録として残せます。

### テストスクリプト（`tools/dify-test/`）

`README.md` に使い方があります。`DIFY_API_KEY` を設定すれば、
どの環境からでも同じ検証を再実行できます。

```bash
export DIFY_API_KEY='app-xxxxxxxx'
python3 full_verify.py        # 着地 → 再開 → 追記 の通し確認
python3 crisis_verify.py      # 危機速報（必要度8以上）
python3 summary_verify.py     # サマリーの項目割り当て
python3 adversarial_codenode_test.py   # コードノードの敵対的テスト
python3 dify.py テスト用ID "発話" ""  '{}'   # 1往復だけ流して全ノードを見る
```

**この方法の利点**：Dify の画面では見えない
パラメータ抽出の結果・HTTPノードの応答本文・コードノードの出力まで確認できます。
`response_mode: streaming` の `node_finished` イベントを読んでいます。
