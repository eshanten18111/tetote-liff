## 404について：対処の方向を変えることを提案します

### 現状

2つの会話（計14往復）で**2回発生**しました（14%）。
修正前の21%より下がっていますが、サンプルが少なく改善とは断定できません。

発生したターンは応答まで52秒かかっており、
「遅いターンで404になる」という相関はご自身の調査と一致します。

### なぜ待ち行列化で防げないか

**GAS側の処理はすでに1.2〜1.4秒です。** 残っている遅さはGASの中ではなく、
**Googleの転送層**にあります。つまり**リクエストがGASに届く前に落ちている**ため、
GAS側をいくら速くしても防げません。ここはこちらから短縮できない部分です。

### 提案：「速くする」から「落ちても失わない」へ

優先順に3つです。

#### 1.【最優先】サマリー保存ノードに、失敗時の退避を入れる

**初回受付は最初の5往復で毎回走るので、1回落ちても次で入ります。**
実際、検証でもそうなっていました。

**しかし引き継ぎサマリーは1回しか送りません。**
ここで404が出たら、**サマリーは永久に失われます。**
しかもGASは受け取っていないので、**GAS側からの通知も飛びません。誰も気づけません。**

9/10に見つけた「Slackには届くが台帳に残らない」と同じ構造の、より悪い版です。

**手順**：サマリー保存ノードの後ろに IF/ELSE を置き、
`status_code ≠ 200` のときに**サマリー本文ごとSlackへ流して**ください。
台帳に入らなくても、内容は残ります。

```
HTTP（相談記録登録：引き継ぎサマリー）
  ↓
IF/ELSE（保存失敗チェック）  条件： status_code ≠ 200
  ├ true → HTTP（保存失敗＋サマリー本文をSlackへ）
  └ false → 従来どおり
```

本文は B と同じく `json.dumps` で組み立ててください（手本ができています）。

#### 2. HTTPノードのリトライ設定を確認する

DifyのHTTPノードにはリトライ設定があります（既定は3回・100ms間隔）。
3ノードとも有効か、間隔が短すぎないかご確認ください。
**転送層の一時的な不調なら、間隔を1〜2秒に広げるだけで拾える可能性があります。**

#### 3. 発生率を継続的に見る

待ち行列化の前後で発生率が変わったかを知りたいところです。
修正前は33件中7回（21%）、私の観測は14件中2回（14%）でサンプル不足です。
5-1を入れればSlackに記録が残るので、自然に集計できます。
