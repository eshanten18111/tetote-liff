## 2.【要確認】追記の退避が飛んだかどうか、私には分かりません

### 何が起きたか

⑭（発言は**「死にたい」**）で、`doGet` の応答が返りました。

```
[HTTP リクエスト（相談記録登録：追記）] status 200
  body: {"ok":true,"message":"soudan log endpoint"}     ← 保存されていない

[コード（追記保存の結果判定）] failed: "true"
  payload: {"text":"🚨 追記を台帳に保存できませんでした…追記の本文：\n死にたい…"}
```

**判定は正しく失敗を検知し、退避本文まで作っています。**

ただし私の取得したストリームには、**その後の送り直しノードもSlack通知ノードも
現れませんでした。**

### 断定できない理由

- 追記の判定ノードは**「回答」より後ろ**に並んでいます（今日、全ノードを取得して確認）。
  応答が返ったあとに続くノードを、私の取得が取りこぼした可能性があります
- ⑭は応答まで**54秒**かかっており、長引いた回でした

**退避が飛んだのに私が見逃した**のか、**本当に飛ばなかった**のか、区別がつきません。

### 確認方法（どちらか一方で分かります）

**方法1：Slackを見る**

9/11 の該当時刻に、こういう通知が届いていませんか。

```
🚨 追記を台帳に保存できませんでした
…
追記の本文：
死にたい
```

**方法2：Difyのログを見る**

| 項目 | 値 |
|---|---|
| 会話ID | `a8cb9b20-6362-4f69-9138-ab67afe2132a` |
| `dialogueCount` | 14 |
| 発言 | 死にたい |

`IF/ELSE 13（追記保存の失敗チェック）` の結果と、その先のノードが動いたかを見てください。

### 結果によって変わること

| Slackに届いていた | **追記の失敗経路は本番で端から端まで通った**ことになります。サマリー側も同じ作りなので、「やらない」というご判断の裏づけが1つ増えます |
|---|---|
| **届いていなかった** | **`IF/ELSE 13` の条件か配線に問題があります。** 同じ作りのサマリー側も動かない可能性が高いので、優先して調べてください |

### 補足：これは作った失敗ではありません

「死にたい」という発言の保存で、たまたま `doGet` の応答が返りました。

**判定を `status_code` だけにしていたら、この訴えは台帳にもSlackにも
残らないまま消えていたはずです。**
`"ok":true` まで見る判定にされた判断が、いちばん重い場面で効いたことになります。

## 3. サマリー保存の失敗分岐について

「やらない（404が自然に出たらログで確認）」というご判断に同意します。

意図的に失敗させるには本番を止める必要があり、**得られるものに対して代償が大きい**です。

そのうえで、上記2の確認結果が判断材料になります。
**追記側で退避が実際に飛んでいれば、同じ作りのサマリー側の残存リスクは
配線だけに絞られます。**

なお、本日の観測では `doGet` の応答は **14〜18往復に1回**程度の頻度で出ています。
着地を何度か繰り返せば、いずれサマリー側でも自然に引けるはずです。
